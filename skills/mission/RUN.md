# Run

Phase Overview (`Docs/wip/task/<slug>/<slug>-phases-overview.md`) 의 Phase 하나를 진행한다. Overview 헤더에는 Plan 경로, base, 부모 브랜치가 있고, 각 Phase 는 `## P{N} <제목> [상태]` 아래에 목표, 범위, 완료 기준, `기록` 을 가진다. Phase 의존은 선형이다. Plan 은 헤더가 가리키는 문서다.

Overview 문서를 남기며 작업하는 목적은, 작업이 모두 끝났을 때 ADR 을 누락 없이 쓰기 위해서다. ADR 의 재료는 Plan 의 설계 결정 표와 Overview 의 Phase 별 `기록` 두 곳뿐이다. 그래서 실행 중에 생긴 것은 그 순간 `기록` 에 남긴다.

## 기록

Phase 항목의 `기록:` 아래에 한 줄씩 덧붙인다. 세 조건으로 거르지 않고 전부 적는다: 무엇을 ADR 로 남길지는 미션이 끝날 때 거른다.

```markdown
- 기록:
  - [결정] <무엇을 정했나> — 이유: <…> / 버린 대안: <…>
  - [변경] 계획: <Plan 이 정한 것> → 실제: <한 것> — 이유: <…>
  - [발견] <계획 때 몰랐던 사실> — 영향: <…>
```

이유는 사용자가 말했거나 작업 중 확인한 것만 쓴다.

## 1. 시작

1. Phase 를 고른다: 지정받은 `P{N}`, 없으면 `[진행중]` Phase, 그것도 없으면 첫 `[미착수]` Phase. `[진행중]` Phase 는 이전 세션의 작업을 이어서 한다: Overview 와 Phase 브랜치의 변경을 읽고 남은 일부터 한다.
2. 앞 Phase 가 `[완료]` 가 아니면 경고한다.
3. 목표와 완료 기준을 보여주고 확인받은 뒤 상태를 `[진행중]` 으로 바꾼다.

## 2. 브랜치

base 브랜치에서 부모 브랜치를 따고, 각 Phase 브랜치는 부모 브랜치에서 딴다. Phase 브랜치의 변경은 부모 브랜치로 PR 한다. 커밋·PR 방식은 프로젝트와 사용자에게 맡긴다.

- 이름은 레포의 최근 브랜치 이름에서 관례를 읽어 제안한다. 관례가 없으면 부모는 `<slug>`, Phase 는 `<slug>-p{N}` 이다. 부모 이름 아래 경로로 짓는 `<slug>/p{N}` 은 git 이 거부한다.
- 첫 Phase 에서 base 를 확인받고 부모 브랜치를 만든 뒤, 두 이름을 Overview 헤더에 적는다.
- Phase 브랜치를 따기 전에 앞 Phase 가 부모에 머지됐는지 확인하고, 부모를 최신으로 맞춘다.
- 브랜치 생성과 전환은 사용자 확인 후 한다.

## 3. Phase 설계

이 스킬 디렉토리 기준 `../grilling/SKILL.md` 를 따른다. 사용자가 교차 검증을 요청하면 `../cross-grilling/SKILL.md` 를 따른다. 범위는 이번 Phase 에서 Plan 이 아직 정하지 않은 것이다: Plan 표에 있는 결정은 다시 묻지 않는다. 확정된 결정은 그 자리에서 `기록` 에 `[결정]` 으로 적는다.

- interface 와 seam 을 정하는 질문은 `../codebase-design/SKILL.md` 의 용어와 원칙으로 판단한다.
- 이번 Phase 에 테스트할 동작이 있으면 테스트 seam 을 질문으로 다룬다. 후보 seam 마다 무엇을 잡고 무엇을 놓치는지 한 줄씩 붙이고, 합의한 seam 을 `[결정]` 으로 적는다.
- 이번 Phase 에 UI 작업이 있으면 UI 테스트를 할지 묻는다. 하기로 하면 검증 시나리오를 질문으로 함께 정한다: 시나리오마다 입력, 기대하는 화면 변화, 판정 근거 (화면, 데이터 값). 합의한 시나리오를 `[결정]` 으로 적는다.
- 열린 결정이 없으면 그렇게 알리고 구현으로 넘어간다.

## 4. 구현과 리뷰

`../implement/SKILL.md` 를 따른다. 넘기는 것: 3 에서 합의한 테스트 seam, 명세로 쓸 이번 Phase 의 목표·범위·완료 기준과 Plan, 리뷰 기준점인 부모 브랜치.

- 이번 Phase 의 범위와 Plan 결정 안에서 작업한다. 벗어난 것과 새로 알게 된 것은 그 순간 `기록` 에 적는다.
- 계획이 두 가지 이상으로 읽히거나 범위 밖 변경이 필요하면 선택지와 추천을 들고 사용자에게 묻는다. 그 답에 기대지 않는 작업은 계속한다.
- 리뷰에서 받아들여 고친 지적은 `기록` 에 `[변경]` 으로 출처 (리뷰 축과 번호) 와 함께 적는다.
- UI 테스트를 하기로 했으면 구현과 리뷰가 끝난 뒤 합의한 시나리오를 체크리스트로 삼아 `../ios-sim-test/SKILL.md` 를 따른다. "판단 필요" 와 실패 항목은 사용자와 정한 뒤 고치거나 `기록` 에 남긴다.
- 완료 기준을 하나씩 확인한다. 에이전트가 확인할 수 없는 항목 (실기기 동작, 화면 확인) 은 체크리스트로 사용자에게 요청한다.
- 끝나면 diff 를 다시 읽어 의도하지 않은 변경을 걷어내고, diff 를 Plan 과 대조해 `기록` 에 빠진 결정·변경·발견을 채운다.

## 5. 완료

다음을 모두 만족하면 Phase 를 `[완료]` 로 바꾼다:

1. 빌드·테스트가 green 이다.
2. 완료 기준을 모두 확인했다. 사람이 확인할 항목은 사용자 확인까지 받았다.
3. `기록` 점검을 마쳤다.
4. 사용자가 이 Phase 를 끝내도 된다고 확인했다.

그다음 다음 `[미착수]` Phase 를 알린다. 마지막 Phase 였으면 그렇다고 알린다.
