리팩터링하는 동안 코드는 항상 동작하므로 언제든 멈출 수 있다. 이 스킬은 그 상태를 지키는 레일이다. 한 번에 새 구조로 다시 쓰는 것은 재작성이다: 중간에 멈출 수 없고, 동작 보존을 증명할 수 없고, 되돌릴 지점이 시작점 하나뿐이다.

대상은 사용자가 준다: 파일·타입, 모듈, 또는 증상 ("여기 고칠 때마다 세 군데를 고친다"). 대상이 없으면 무엇을 리팩터링할지 묻는다.

## 규칙

모든 Phase 에 적용한다.

1. **two hats**: 기능 추가·버그 수정과 재구성은 다른 스텝에 둔다. 요청에 섞여 있으면 재구성분만 받고 나머지는 분리해 두자고 제안한다. 리팩터링 중 찾은 버그는 그대로 둔 채 구조만 옮기고 종료 보고로 넘긴다.
2. **동작 보존**: 관찰 가능한 동작이 그대로인 변경만 리팩터링이다.
3. Phase 0~2 는 읽기만 한다. 편집은 백로그 승인 뒤 Phase 3 에서 시작한다.
4. **1 스텝 = 1 기법 = 1 커밋**. rename 과 move 는 다른 커밋에 둔다: git 이 rename 을 추적하고 diff 가 읽힌다.
5. 스텝 끝이 red 면 되돌리고 (`git restore`) 스텝을 더 잘게 쪼갠 뒤 다시 한다.
6. 진단과 제안이 기대는 사실은 명령 출력으로 확인한다. 확인 못 한 것은 `(미검증)` 으로 쓴다. 파일명이 비슷하거나 디렉토리가 가깝다는 것은 정황일 뿐이다.
7. 지금 필요한 구조만 만든다 (YAGNI). 쓰이지 않을 유연성은 *Speculative Generality* 를 새로 만드는 일이다.
8. 명료성이 먼저다. 성능을 이유로 구조를 바꾸는 것은 측정한 뒤에 한다.

### 착수하지 않는 대상

다음이면 레일을 깔지 않고 그 판단을 보고한다: 무엇을 하는지 아직 설명할 수 없는 코드 (먼저 읽는다), 재작성이 나은 코드 (재작성 권고), 곧 삭제·대체될 코드, 안전망을 만들 수 없는 코드 (Phase 1 에서 판정한다. 범위를 좁히거나 중단한다).

리팩터링 도중 호출처 0 을 grep 등으로 **증명**한 도달 불가 코드는 별도 커밋으로 지운다. 못 찾았다는 정황만 있으면 그대로 둔다.

## Phase 0 — 접수

네 줄로 보고한다.

- 대상: 파일 경로와 줄 수, 또는 모듈. 증상으로 받았으면 여기서 파일로 바꾼다.
- 모자: 요청에 기능 변경이 섞였는지.
- 규모: 파일·타입 하나면 Phase 3 으로 끝난다. 공개 계약, 모듈 사이 seam, 여러 모듈의 호출처에 걸치면 이 스킬 디렉토리의 `SYSTEM-SCALE.md` 를 Phase 3 에서 함께 따른다.
- 착수 가능 여부.

## Phase 1 — 안전망 (게이트 1)

green 을 정의한다. 프로젝트의 지침 문서 (`CLAUDE.md`, `AGENTS.md` 등), `Makefile`, `package.json` 같은 곳에서 테스트·빌드·lint 명령을 찾아 명령 그대로 적는다. 화면을 건드리면 사람이 확인할 항목도 적는다. Phase 3 의 모든 스텝을 이 정의로 판정한다.

대상의 동작을 고정하는 테스트가 없으면 **characterization test** 를 먼저 쓴다. 올바른 동작이 아니라 현재 동작을, 버그까지 그대로 기록한다. 다음을 만족해야 안전망으로 인정한다:

- 대상에 일시적으로 오류를 심어 테스트가 실제로 실패하는지 확인하고, 오류를 되돌린다.
- 경계 조건 (빈 값, null, 경계 인덱스, 실패 응답) 처럼 망가질 수 있는 곳을 덮는다.
- 테스트 하나에 검증 하나다.

characterization test 는 리팩터링이 아니므로 별도 커밋으로 먼저 넣는다.

게이트: green 명령, 기존 테스트 현황 (실측), 새로 쓸 characterization test 목록, 비용 추정을 보여주고 승인받는다. 사용자가 테스트 없이 진행을 고르면 그 결정을 기록하고, 이후 작업이 무보증 재구성이라고 한 줄로 밝힌다.

## Phase 2 — 악취 지도 (게이트 2)

대상을 읽고 Fowler 의 code smell 이름 (영어 원어: *Long Function*, *Large Class*, *Shotgun Surgery* …) 으로 진단한다. 이름을 붙일 수 없는 인상 ("좀 복잡하다") 은 목록에 넣지 않는다.

- 파일부터 센다. 파일 하나에 최상위 타입이 여럿이면 파일 분리를 백로그 1번에 둔다: 그 위에서 다른 기법을 돌려야 diff 가 읽힌다.
- 항목마다 위치 (`file:line` 이나 심볼), 처방 기법 (Fowler 기법 영어 원어), 스텝 수, 위험을 단다.
- 진단에 쓴 측정 (줄 수, 타입·필드·멤버 수 등) 과 그 명령을 적어 둔다. 재측정에 같은 자를 쓴다.
- 이미 사라져서 뺀 항목은 어느 커밋에서 사라졌는지 적는다 (`git log -S'<특징적 조각>' --oneline`). 그래야 진단 중에 고친 것이 아님이 드러난다.
- 진단에 *Shotgun Surgery*, *Duplicated Code*, *Repeated Switches* 가 있으면 이 스킬 디렉토리의 `CO-REFACTOR.md` 로 함께 고칠 대상을 실측한다.
- *Middle Man*, *Speculative Generality*, *Shotgun Surgery* 는 `../codebase-design/SKILL.md` 의 원칙으로 판정한다: 지워도 복잡도가 호출처에 다시 나타나지 않으면 (deletion test) *Middle Man*, 운영·테스트를 합쳐 adapter 가 하나뿐인 seam 은 *Speculative Generality*, 흩어진 편집은 locality 부족이다. 여러 shallow module 을 합쳐야 풀리면 `../codebase-design/DEEPENING.md` 로 의존성을 분류하고, 처방은 Fowler 기법 (*Inline Class*, *Combine Functions into Class* 등) 으로 적는다.

```
| # | smell        | 위치               | 기법            | 스텝 | 위험 |
|---|--------------|--------------------|-----------------|------|------|
| 1 | Long Function | OrderService:412  | Extract Function | 4    | 낮음 |
| 2 | Large Class   | OrderService 전체 | Extract Class    | 9    | 높음 |
```

순서는 저수준·저위험이 먼저, 큰 구조 변경이 나중이다. 작은 정리를 끝내 두면 큰 변경의 diff 가 읽힌다.

게이트: 백로그와 함께 고칠 대상 실측 결과를 보여주고 승인받는다. 기각된 후보는 백로그에 메모로 남긴다.

## Phase 3 — 실행 루프

백로그를 위에서부터 한 스텝씩 한다. 스텝마다:

1. 기법 하나를 고르고, Fowler 가 쓴 그 기법의 절차를 단계 그대로 밟는다. 위임 함수를 거치거나 필드를 하나씩 옮기는 중간 단계가 언제든 멈출 수 있는 상태를 만든다.
2. 새로 만들거나 옮기는 것의 위치는 이름이 아니라 그것을 쓰는 곳 (소비처) 과 프로젝트 지침 문서로 정한다.
3. Phase 1 의 명령으로 green 을 직접 확인한다.
4. 무엇을 어느 기법으로 했는지 드러나는 메시지로 커밋한다.

- 한 스텝에 두 번째 기법이 필요해지면 스텝을 쪼갠다.
- 눈에 띈 다른 악취는 백로그에 추가하고 지금 스텝을 마친다.
- 몇 스텝마다 테스트 범위를 넓혀 전체를 돌린다.
- 하위 에이전트에 맡길 때는 스텝 하나만 넘기고, green 확인과 커밋은 직접 한다.
- 백로그에 진행 위치를 표시해 사용자가 언제든 멈출 수 있게 한다.

## 연속 실행

두 게이트의 승인은 대상이 끝날 때까지 유효하다. 그 뒤로는 보고하고 그대로 진행한다. 다음 다섯 경우에만 멈추고 묻는다: 재작성을 권고하게 됐을 때, 공개 계약을 바꿔야 할 때, 안전망을 만들 수 없을 때, 사용자만 답할 수 있는 판단 (제품 동작 의도 등) 이 필요할 때, 백로그에 없던 변경이 필요할 때.

## 재측정과 완료

완료 기준은 진단 해소다. 백로그를 비운 것이 아니다. 백로그가 끝나면 Phase 2 의 측정을 같은 명령으로 다시 재서 숫자로 보고한다. 목표에 못 미치면 남은 항목을 백로그에 다시 올려 이어서 돈다. 남은 항목에 안전망이 없으면 Phase 1 의 characterization test 부터 쓴다.

- *Large Class* 는 줄 수가 아니라 필드·멤버 수로 판정한다. 줄 수는 *Extract Function* 으로도 움직이지만 필드·멤버 수는 협력자를 실제로 떼어내야 줄어든다.
- 백로그가 *Extract Function* 위주였다면 파일이 그대로거나 늘어도 정상이다: 가독성 기법이다.
- *Extract Class* 를 했는데 파일이 그대로면 추출한 타입이 같은 파일에 남아 있다. 최상위 타입 수를 다시 센다.

## 종료 보고

완주했든 중간에 멈췄든 남긴다:

- 처리: 어떤 악취를 어떤 기법으로, 몇 커밋에 걸쳐 없앴나
- 보류: 남은 백로그와 이유
- 기각: 리팩터링이 아니라고 판정한 것. 재작성 권고는 따로 적는다
- 안전망 변화: 새 characterization test, 여전히 비어 있는 곳
- 발견한 버그: 버그를 드러내는 테스트부터 쓰도록 넘긴다
