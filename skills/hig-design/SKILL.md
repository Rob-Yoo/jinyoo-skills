사용자가 준 기능 설명으로 iPhone 화면을 설계한다. 산출물은 `Docs/wip/design/<slug>/` 의 두 파일이다.

- `spec.md`: 화면 설계서. 구현하는 에이전트가 읽는다.
- `prototype.html`: 사람이 브라우저에서 클릭해 보는 프로토타입. 오프라인 단일 파일.

코드는 쓰지 않는다. 설계서는 구현 프레임워크를 가정하지 않는다: 컴포넌트는 HIG 의 이름 (Tab bar, Sheet, Search field …), 전환과 애니메이션은 범용 용어 (push, modal sheet, cross-fade …) 로 쓰고 특정 프레임워크의 API 이름은 쓰지 않는다.

## 규칙

- **기존 앱이 먼저다.** 코드에 이미 있는 색, 폰트, 커스텀 컴포넌트, 내비게이션 구조를 그대로 쓰고, 없는 부분만 HIG 표준으로 채운다. 기존 디자인이 HIG 와 어긋나는 곳은 설계서의 "HIG 와 다른 점" 에 적기만 하고 바꾸지 않는다.
- **접근성은 예외다.** 새로 설계하는 화면에서는 터치 영역, 대비, 큰 글자 크기, 스크린 리더, 동작 줄이기를 HIG 대로 지킨다. 기존 디자인을 따르다 이것들이 깨지면 HIG 쪽을 택하고 "HIG 와 다른 점" 에 이유를 적는다.
- **HIG 근거는 이 스킬 디렉토리의 `REFERENCE.md` 에서 찾는다.** 요약만으로 판단이 서지 않으면 원문을 받아 확인한다: `https://developer.apple.com/tutorials/data/design/human-interface-guidelines/<slug>.json`. 근거로 적는 링크는 사람이 읽는 주소 `https://developer.apple.com/design/human-interface-guidelines/<slug>` 다.
- **정하지 못한 것은 정하지 않는다.** 요구사항과 코드로 답이 안 나오는 것은 설계서의 "열린 질문" 에 적고 사용자에게 넘긴다.

## 단계

1. **읽기**: 기능 설명, 프로젝트 지침 문서, 기존 앱 코드를 읽는다. 찾을 것: 색·폰트 정의, 재사용 중인 커스텀 컴포넌트, 탭과 내비게이션 구조, 이 기능이 붙을 자리.
2. **구조 합의**: 화면 목록과 내비게이션 트리를 텍스트로 보여주고 확인받는다. slug 도 이때 함께 정한다. 트리가 틀리면 두 파일을 통째로 다시 만들어야 하므로, 확인 전에는 파일을 만들지 않는다.

   ```
   slug: order-history
   [탭] 주문
     S1 주문 내역 ─push→ S2 주문 상세 ─alert→ S4 주문 취소 확인
               └─sheet→ S3 필터
   ```

3. **설계서**: 아래 형식으로 `spec.md` 를 쓴다.
4. **프로토타입**: 이 스킬 디렉토리의 `PROTOTYPE.md` 를 읽고 그대로 `prototype.html` 을 만든다. 설계서의 화면·요소마다 프로토타입에 같은 S 번호의 `data-spec` 이 있어야 한다.
5. **확인**: `python3 <이 스킬 디렉토리>/scripts/check-ids.py Docs/wip/design/<slug>` 로 S 번호가 1:1 인지 확인한다. 어긋나면 고친다. 브라우저를 다룰 수 있으면 프로토타입을 열어 모든 이동과 상태 전환을 한 번씩 눌러 보고 콘솔 오류가 없는지 본다.
6. **피드백**: 두 파일 경로를 알려주고 프로토타입을 열어 보게 한다. 피드백은 두 파일에 함께 반영하고 5 를 다시 돌린다.

## 설계서 형식

```markdown
# <기능> 화면 설계
> 작성: YYYY-MM-DD · 프로토타입: prototype.html · 플랫폼: iPhone

## 내비게이션
<2 에서 합의한 트리>

## S1 <화면 이름>
- 목적: <사용자가 이 화면에서 하는 일 한 줄>
- 진입: <출발 화면> → <전환: push | modal sheet | full-screen cover | tab switch>
- 구성:
  - S1.1 <요소> — <HIG 컴포넌트명> · <동작> · HIG: <링크>
- 전환·애니메이션: <트리거> → <효과: push / dismiss / cross-fade / expand 등> · 시스템 기본 | 커스텀 (<시간>, <곡선>)
- 상태: 기본 / 빈 / 로딩 / 오류 — 각각 무엇을 보여주나
- 접근성: 스크린 리더 레이블, 큰 글자 크기에서의 배치, 터치 영역, 동작 줄이기 시 대체 효과

## HIG 와 다른 점
- <위치> — <어긋난 규칙> · <기존 디자인을 따른 이유 또는 접근성 때문에 HIG 를 택한 이유> · HIG: <링크>

## 열린 질문
- <설계 중 정하지 못한 것>
```

화면 번호는 `## S1`, 요소 번호는 `- S1.1` 형식을 지킨다. `check-ids.py` 가 이 형식으로 번호를 읽는다. 상태가 하나뿐인 화면은 "상태" 줄에 그렇게 적는다.

## 완료

두 파일이 만들어지고, `check-ids.py` 가 통과하고, 사용자가 프로토타입을 보고 더 고칠 것이 없다고 하면 끝난다. 끝나면 이 한 줄을 남긴다: "구현에 다 쓰면 `Docs/wip/design/<slug>/` 를 지워라."
