`HEAD` 와 기준점 사이의 diff 를 두 축으로 리뷰한다:

- **Standards**: 코드가 이 프로젝트에 문서로 정해진 코딩 기준을 따르는가?
- **Spec**: 코드가 출발점이 된 명세를 충실히 구현하는가?

두 축은 서로의 판단을 오염시키지 않도록 **반대편 에이전트에게 따로, 병렬로** 맡기고, 이 스킬이 결과를 모은다.

## 절차

### 1. 기준점을 고정한다

사용자가 말한 것이 기준점이다 (커밋 SHA, 브랜치, 태그, `main`, `HEAD~5` 등). 말하지 않았으면 묻는다.

기준점이 실제로 있는지 (`git rev-parse <기준점>`) 와 diff 가 비어 있지 않은지 먼저 확인한다. 잘못된 ref 나 빈 diff 는 리뷰어를 띄우기 전에 여기서 걸러야 한다. 그다음 diff 를 파일로 저장하고 (`git diff <기준점>...HEAD > "$(mktemp)"`, 세 점이라 merge-base 기준이다) 커밋 목록 (`git log <기준점>..HEAD --oneline`) 을 적어 둔다. 리뷰어가 git 을 실행할 수 없어도 diff 파일은 읽을 수 있다.

### 2. 명세를 찾는다

호출한 쪽이 명세 (문서 경로, 또는 이번 작업의 목표·범위·완료 기준) 를 줬으면 그것을 쓴다. 없으면 사용자가 준 경로, 또는 이번 브랜치·기능 이름과 맞는 명세 파일을 찾는다. 그래도 없으면 사용자에게 묻고, 명세가 없다고 하면 Spec 축은 건너뛰고 "명세 없음" 으로 보고한다.

### 3. 기준 문서를 찾는다

코드 작성법을 정한 파일을 레포에서 모두 찾는다 (`CODING_STANDARDS.md`, `CONTRIBUTING.md`, `CLAUDE.md`, `AGENTS.md` 등). `CODING_STANDARDS.md` 나 `CONTRIBUTING.md` 가 있으면 반드시 목록에 넣는다.

레포가 무엇을 문서로 정했든, Standards 축은 아래 **smell baseline** 을 항상 함께 들고 간다: Fowler 『Refactoring』 3장의 code smell 일부로, 레포가 아무것도 정하지 않았어도 적용된다. 두 규칙이 묶는다:

- **레포가 이긴다.** 문서로 정한 레포 기준이 언제나 우선한다. baseline 이 지적할 것을 레포가 승인했다면 그 smell 은 지적하지 않는다.
- **언제나 판단의 문제다.** 각 smell 은 "possible Feature Envy" 처럼 이름 붙인 휴리스틱이지 명백한 위반이 아니다. 도구가 이미 강제하는 것은 건너뛴다.

각 smell 은 _무엇인가_ → _어떻게 고치나_ 로 읽고 diff 와 대조한다:

- **Mysterious Name**: 하는 일이나 담은 것을 드러내지 않는 함수·변수·타입 이름. → 이름을 바꾼다. 정직한 이름이 떠오르지 않으면 설계가 흐린 것이다.
- **Duplicated Code**: 같은 로직 모양이 변경 안 여러 hunk·파일에 나온다. → 공통 모양을 추출해 양쪽에서 부른다.
- **Feature Envy**: 자기 데이터보다 다른 객체의 데이터를 더 많이 건드리는 메서드. → 그 데이터가 있는 곳으로 메서드를 옮긴다.
- **Data Clumps**: 같은 필드·매개변수 몇 개가 늘 함께 다닌다 (태어나고 싶은 타입). → 하나의 타입으로 묶어 넘긴다.
- **Primitive Obsession**: 자기 타입을 가질 만한 도메인 개념을 원시값이나 문자열이 대신한다. → 그 개념에 작은 타입을 준다.
- **Repeated Switches**: 같은 타입에 대한 같은 `switch`/`if` 연쇄가 변경 곳곳에 반복된다. → 다형성으로 바꾸거나 두 곳이 함께 쓰는 map 하나로.
- **Shotgun Surgery**: 논리적 변경 하나가 diff 안 여러 파일에 흩어진 편집을 강제한다. → 함께 바뀌는 것을 한 모듈로 모은다.
- **Divergent Change**: 파일·모듈 하나가 서로 무관한 여러 이유로 편집된다. → 모듈마다 한 가지 이유로 바뀌게 나눈다.
- **Speculative Generality**: 명세에 없는 필요를 위해 넣은 추상화·매개변수·훅. → 지우고, 실제 필요가 보일 때까지 인라인한다.
- **Message Chains**: 호출자가 기대지 말아야 할 긴 `a.b().c().d()` 탐색. → 첫 객체의 메서드 하나 뒤로 숨긴다.
- **Middle Man**: 대부분 그냥 다른 곳에 위임하는 클래스·함수. → 걷어내고 실제 대상을 바로 부른다.
- **Refused Bequest**: 물려받은 것을 대부분 무시하거나 덮어쓰는 하위 클래스·구현체. → 상속을 버리고 합성을 쓴다.

### 4. 두 리뷰어를 병렬로 띄운다

이 스킬 디렉토리 기준 `../second-opinion/SKILL.md` 의 프롬프트 규칙을 따르고, `../second-opinion/scripts/ask.sh` 로 반대편 에이전트 (Claude 면 codex, Codex 면 claude) 를 두 번, 동시에 부른다. second-opinion 의 확인 게이트는 건너뛴다. 반대편 호출이 실패하면 그 축은 같은 호스트의 하위 에이전트로 대신하고 보고에 그 사실을 적는다.

**Standards 리뷰어** 프롬프트에 넣는 것:

- diff 파일 경로와 커밋 목록
- 3단계에서 찾은 기준 문서 목록, 그리고 3단계의 smell baseline 전문 (리뷰어는 달리 접근할 길이 없다)
- 요청: "파일·hunk 별로 (a) diff 가 문서로 정한 기준을 어긴 모든 곳: 기준을 인용하라 (파일 + 규칙), (b) 보이는 baseline smell: 이름을 대고 hunk 를 인용하라. 명백한 위반과 판단의 문제를 구별하라: 문서 기준 위반은 명백할 수 있지만 baseline smell 은 언제나 판단의 문제이고, 문서로 정한 레포 기준이 baseline 보다 우선한다. 도구가 강제하는 것은 건너뛰어라. 400 단어 이내."

**Spec 리뷰어** 프롬프트에 넣는 것:

- diff 파일 경로와 커밋 목록
- 명세의 경로나 내용
- 요청: "(a) 명세가 요구했는데 빠졌거나 일부만 된 것, (b) diff 에 있는데 요구되지 않은 동작 (범위 초과), (c) 구현된 것 같지만 구현이 틀려 보이는 요구사항을 보고하라. 항목마다 명세의 해당 줄을 인용하라. 400 단어 이내."

명세가 없으면 Spec 리뷰어는 띄우지 않고 최종 보고에 적는다.

### 5. 모은다

두 보고를 `## Standards` 와 `## Spec` 아래에 그대로, 또는 가볍게 다듬어 보여준다. 두 축은 일부러 분리한 것이므로 지적을 합치거나 순위를 다시 매기지 않는다.

마지막에 한 줄 요약: 축별 지적 수, 그리고 _각 축 안에서_ 가장 심각한 문제. 두 축을 통틀어 하나를 고르지 않는다: 그것이 분리가 막으려는 재정렬이다.

## 왜 두 축인가

변경은 한 축을 통과하고 다른 축에 실패할 수 있다:

- 모든 기준을 따랐지만 엉뚱한 것을 구현한 코드 → **Standards 통과, Spec 실패.**
- 요구한 그대로 했지만 프로젝트 관례를 깬 코드 → **Spec 통과, Standards 실패.**

따로 보고하면 한 축이 다른 축을 가리지 않는다.
