# Design It Twice

deepening 후보로 고른 모듈에 다른 interface 를 탐색하고 싶을 때 쓰는 병렬 하위 에이전트 패턴. Ousterhout 의 "Design It Twice" 에 기댄다: 첫 아이디어가 최선일 가능성은 낮다.

[SKILL.md](SKILL.md) 의 용어를 쓴다: **module**, **interface**, **seam**, **adapter**, **leverage**.

## 절차

### 1. 문제 공간을 잡는다

하위 에이전트를 띄우기 전에, 고른 후보의 문제 공간을 사용자에게 설명한다:

- 새 interface 가 충족해야 할 제약
- 기댈 의존성과 각각의 분류 ([DEEPENING.md](DEEPENING.md) 참고)
- 제약을 구체화하는 대략적인 코드 스케치. 제안이 아니라 제약을 손에 잡히게 하는 용도다

이것을 보여주고 바로 2단계로 간다. 하위 에이전트가 병렬로 일하는 동안 사용자가 읽고 생각한다.

### 2. 하위 에이전트를 띄운다

하위 에이전트 3개 이상을 병렬로 띄운다. 각자 deepen 된 모듈의 interface 를 **근본적으로 다르게** 만들어야 한다.

각 하위 에이전트에게 따로 기술 브리프를 준다 (파일 경로, 결합 상세, [DEEPENING.md](DEEPENING.md) 의 의존성 분류, seam 뒤에 무엇이 있는지). 브리프는 1단계의 사용자용 설명과 별개다. 각자에게 다른 설계 제약을 준다:

- 에이전트 1: "interface 를 최소로: 진입점 최대 1~3개. 진입점당 leverage 를 최대로."
- 에이전트 2: "유연성을 최대로: 많은 사용 사례와 확장을 지원."
- 에이전트 3: "가장 흔한 호출자에 최적화: 기본 사례를 사소하게."
- 에이전트 4 (해당하면): "seam 을 넘는 의존성은 ports & adapters 로 설계."

브리프에 [SKILL.md](SKILL.md) 의 용어와 프로젝트가 쓰는 도메인 용어를 함께 넣어, 각 하위 에이전트가 아키텍처 용어와 도메인 용어로 일관되게 이름 붙이게 한다.

각 하위 에이전트의 산출:

1. Interface (타입, 메서드, 매개변수, 그리고 불변식, 순서, 오류 방식)
2. 호출자가 쓰는 사용 예시
3. implementation 이 seam 뒤에 숨기는 것
4. 의존성 전략과 adapter ([DEEPENING.md](DEEPENING.md) 참고)
5. 트레이드오프: leverage 가 높은 곳, 얇은 곳

### 3. 보여주고 비교한다

설계를 하나씩 차례로 보여줘 사용자가 소화하게 한 뒤, 산문으로 비교한다. **depth** (interface 에서의 leverage), **locality** (변경이 모이는 곳), **seam 위치** 로 대조한다.

비교한 뒤 네 추천을 준다: 어느 설계가 가장 강하다고 보는지와 그 이유. 여러 설계의 요소가 잘 결합되면 혼합안을 제안한다. 분명하게 말한다: 사용자는 메뉴가 아니라 확실한 판단을 원한다.
