# Test-Driven Development

TDD 는 red → green 루프다. 이 스킬은 그 루프가 남길 가치가 있는 테스트를 만들게 하는 reference 다: 좋은 테스트란 무엇인가, 테스트는 어디에 두나, anti-pattern, 루프 규칙. 모든 섹션이 매 사이클에 적용된다: 루프가 끝난 뒤가 아니라 루프 전과 도중에 본다.

손대는 영역에 ADR 이 있으면 읽고 그 결정을 지킨다. ADR 위치는 이 스킬 디렉토리 기준 `../grill-with-adr/ADR-FORMAT.md` 를 따른다.

## 좋은 테스트란

테스트는 implementation 세부가 아니라 공개 interface 를 통해 동작을 검증한다. 코드는 통째로 바뀔 수 있지만 테스트는 바뀌지 않아야 한다. 좋은 테스트는 명세처럼 읽힌다: "user can checkout with valid cart" 는 어떤 능력이 있는지 정확히 말하고, 내부 구조에 관심이 없으므로 리팩터링에도 살아남는다.

예시는 이 스킬 디렉토리의 [tests.md](tests.md), mock 지침은 [mocking.md](mocking.md) 에 있다.

## Seam: 테스트가 놓이는 곳

**seam** 은 모듈의 interface 가 사는 자리다. 테스트는 seam 에서 interface 로 동작을 관찰하고, 내부에 대고 쓰지 않는다.

**미리 합의한 seam 에서만 테스트한다.** 테스트를 쓰기 전에 테스트할 seam 을 적고 사용자에게 확인받는다. 확인받지 않은 seam 에는 테스트를 쓰지 않는다. 모든 것을 테스트할 수는 없으므로, seam 을 먼저 합의하는 것이 테스트 노력을 모든 경계 사례가 아니라 핵심 경로와 복잡한 로직에 쓰게 하는 방법이다.

묻는다: "공개 interface 는 무엇이고, 어느 seam 을 테스트할까?" 제안하는 seam 마다 무엇을 잡고 무엇을 놓치는지 한 줄씩 붙인다.

seam·interface 등 설계 용어의 정의와 판정 원칙은 형제 스킬 `../codebase-design/SKILL.md` 에 있다. 진행할 세션이 아니라 참고할 reference 다. seam 후보를 고를 때 두 원칙을 적용한다: interface 가 곧 테스트 표면이다 (interface 너머를 테스트하고 싶으면 모듈 모양을 의심한다), adapter 하나면 가설의 seam 이다.

## 루프를 쓸지

기댓값을 코드와 독립적으로 정할 수 없는 변경은 red → green 루프 대신 빌드와 기존 테스트로 확인하고, UI 코드는 앱을 실행해 화면에서 확인한다. 판단 로직은 UI 가 아니라 그 결과를 값으로 관찰할 수 있는 seam 에서 테스트한다. 억지로 루프를 돌리면 아래의 tautological 테스트가 나온다.

## Anti-pattern

- **Implementation-coupled**: 내부 협력자를 mock 하거나, private 메서드를 테스트하거나, 우회 경로로 검증한다 (interface 대신 데이터베이스를 조회). 징후: 동작은 그대로인데 리팩터링하면 테스트가 깨진다. 유닛 테스트를 붙이려고 프로덕션 코드에 식별자나 대기 훅을 더해야 한다면, 그 테스트는 판단 로직이 없는 층을 겨누고 있다.
- **Tautological**: 검증이 코드가 계산하는 방식 그대로 기댓값을 다시 계산한다 (`#expect(add(a, b) == a + b)`, 같은 방식으로 손으로 만든 스냅샷, 자기 자신과 같다고 검증하는 상수). 구조상 통과하므로 코드와 결코 어긋날 수 없다. 기댓값은 독립된 출처에서 와야 한다: 검증된 리터럴, 손으로 푼 예제, 명세.
- **Copy-coupled**: 사용자에게 보이는 문구를 통째로 리터럴과 비교한다. 동작은 그대로인데 문구를 다듬으면 깨진다. 문구에 들어가기 전의 동적 값을 검증한다. 문구 리터럴은 문구 조립에 로직이 있을 때만 검증한다.
- **Horizontal slicing**: 테스트를 전부 먼저 쓰고 구현을 전부 나중에 한다. 한꺼번에 쓴 테스트는 _상상한_ 동작을 검증한다: 사용자가 보는 동작 대신 _모양_ 을 테스트하게 되고, 실제 변경에 둔감해지고, implementation 을 이해하기 전에 테스트 구조에 묶인다. 대신 **vertical slice** 로 일한다: 테스트 하나 → 구현 하나 → 반복. 각 테스트는 직전 사이클에서 배운 것에 반응하는 **tracer bullet** 이다.

## 루프 규칙

- **red 가 green 보다 먼저.** 실패하는 테스트를 먼저 쓰고, 그것을 통과시킬 만큼만 코드를 쓴다. 다음 테스트를 미리 내다보거나 추측성 기능을 넣지 않는다.
- **한 번에 한 slice.** 사이클마다 seam 하나, 테스트 하나, 최소 구현 하나.
- **리팩터링은 루프에 속하지 않는다.** 구현의 red → green 사이클이 아니라 리뷰 단계 (`impl-review` 스킬) 의 일이다.
