Phase Overview (`Docs/tmp/task/<slug>/<slug>-phases-overview.md`) 의 Phase 하나를 진행한다. Overview 헤더에는 Plan 경로, base, 부모 브랜치가 있고, 각 Phase 는 `## P{N} <제목> [상태]` 아래에 목표, 범위, 완료 기준, `기록` 을 가진다. Phase 의존은 선형이다. Plan 은 헤더가 가리키는 문서다. 인자는 `P{N}` (생략하면 다음 Phase) 과 `cross` (Phase 설계에 cross-grilling 사용) 다.

Overview 문서를 남기며 작업하는 목적은, 작업이 모두 끝났을 때 ADR 을 누락 없이 쓰기 위해서다. ADR 의 재료는 Plan 의 설계 결정 표와 Overview 의 Phase 별 `기록` 두 곳뿐이다. 그래서 실행 중에 생긴 것은 그 순간 `기록` 에 남긴다.

## 기록

Phase 항목의 `기록:` 아래에 한 줄씩 덧붙인다. 세 조건으로 거르지 않고 전부 적는다: 무엇을 ADR 로 남길지는 미션이 끝날 때 거른다.

```markdown
- 기록:
  - [결정] <무엇을 정했나> — 이유: <…> / 버린 대안: <…>
  - [변경] 계획: <Plan 이 정한 것> → 실제: <한 것> — 이유: <…>
  - [발견] <계획 때 몰랐던 사실> — 영향: <…>
```

이유는 사용자가 말했거나 작업 중 확인한 것만 쓴다.

## 1. 시작

1. `Docs/tmp/task/*/*-phases-overview.md` 를 찾는다. 하나면 그것을 쓰고, 여럿이면 사용자에게 묻는다.
2. Phase 를 고른다: 인자로 받은 `P{N}`, 없으면 `[진행중]` Phase, 그것도 없으면 첫 `[미착수]` Phase. `[진행중]` Phase 는 이전 세션의 작업을 이어서 한다: Overview 와 Phase 브랜치의 변경을 읽고 남은 일부터 한다.
3. 앞 Phase 가 `[완료]` 가 아니면 경고한다.
4. 목표와 완료 기준을 보여주고 확인받은 뒤 상태를 `[진행중]` 으로 바꾼다.

## 2. 브랜치

base 브랜치에서 부모 브랜치를 따고, 각 Phase 브랜치는 부모 브랜치에서 딴다. Phase 브랜치의 변경은 부모 브랜치로 PR 한다. 커밋·PR 방식은 프로젝트와 사용자에게 맡긴다.

- 이름은 레포의 최근 브랜치 이름에서 관례를 읽어 제안한다. 관례가 없으면 부모는 `<slug>`, Phase 는 `<slug>-p{N}` 이다. 부모 이름 아래 경로로 짓는 `<slug>/p{N}` 은 git 이 거부한다.
- 첫 Phase 에서 base 를 확인받고 부모 브랜치를 만든 뒤, 두 이름을 Overview 헤더에 적는다.
- Phase 브랜치를 따기 전에 앞 Phase 가 부모에 머지됐는지 확인하고, 부모를 최신으로 맞춘다.
- 브랜치 생성과 전환은 사용자 확인 후 한다.

## 3. Phase 설계

이 스킬 디렉토리 기준 `../grilling/SKILL.md` 를 따른다. 인자가 `cross` 면 `../cross-grilling/SKILL.md` 를 따른다. 범위는 이번 Phase 에서 Plan 이 아직 정하지 않은 것이다: Plan 표에 있는 결정은 다시 묻지 않는다. 열린 결정이 없으면 그렇게 알리고 구현으로 넘어간다. 확정된 결정은 그 자리에서 `기록` 에 `[결정]` 으로 적는다.

## 4. 구현과 검증

- 직접 구현한다. 프로젝트의 `CLAUDE.md`·`AGENTS.md` 규칙을 따른다.
- 이번 Phase 의 범위와 Plan 결정 안에서 작업한다. 벗어난 것과 새로 알게 된 것은 그 순간 `기록` 에 적는다.
- 계획이 두 가지 이상으로 읽히거나 범위 밖 변경이 필요하면 선택지와 추천을 들고 사용자에게 묻는다. 그 답에 기대지 않는 작업은 계속한다.
- 프로젝트의 빌드·테스트 명령 (`CLAUDE.md`, `Makefile`, `package.json` 등에서 찾는다) 으로 확인하고, green 이 될 때까지 고친다.
- 완료 기준을 하나씩 확인한다. 에이전트가 확인할 수 없는 항목 (실기기 동작, 화면 확인) 은 체크리스트로 사용자에게 요청한다.
- 끝나면 diff 를 다시 읽어 의도하지 않은 변경을 걷어내고, diff 를 Plan 과 대조해 `기록` 에 빠진 결정·변경·발견을 채운다.

## 5. 교차 리뷰

"교차 리뷰할까?" 를 묻는다. 예면 `../second-opinion/SKILL.md` 의 프롬프트 규칙과 실행 방법을 따르되 확인 게이트는 건너뛴다: 상대는 반대편 에이전트, 내 판단 공유는 "함" 이다. 자료는 부모 브랜치 대비 diff 를 저장한 파일 (`git diff <부모>...HEAD > "$(mktemp)"`), Plan, Overview 다. 질문은 이렇다.

> 이번 Phase 변경을 검토하라: 목표와 완료 기준을 충족하는가, Plan 결정과 어긋나는가, 버그나 빠진 경우가 있는가.

결과는 second-opinion 형식으로 보여주고, 받아들일 지적과 넘길 지적을 나눠 알린다. 받아들인 지적은 고치고 다시 검증한 뒤, `기록` 에 `[변경]` 으로 출처 (리뷰 N번) 와 함께 적는다.

## 6. 완료

다음을 모두 만족하면 Phase 를 `[완료]` 로 바꾼다:

1. 빌드·테스트가 green 이다.
2. 완료 기준을 모두 확인했다. 사람이 확인할 항목은 사용자 확인까지 받았다.
3. `기록` 점검을 마쳤다.
4. 사용자가 이 Phase 를 끝내도 된다고 확인했다.

그다음 다음 `[미착수]` Phase 를 알린다. 마지막 Phase 였으면 미션 종료를 안내한다: Plan 의 설계 결정 표와 Overview 의 `기록` 으로 ADR 을 쓰고 (`../grill-with-adr/ADR-FORMAT.md`), `Docs/tmp/plan/<slug>.md` 와 `Docs/tmp/task/<slug>/` 를 정리할 차례다.
