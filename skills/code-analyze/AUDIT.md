# 감사 branch

[`code-analyze`](SKILL.md) 의 branch 다: 기존 코드에서 결함 후보를 찾을 때 읽는다. 등급과 재확인은 SKILL.md 를 따르고, 산출은 보고서 파일이다.

## 1. 범위를 정한다

- 감사할 범위 (레포 전체, 특정 기능) 와 보고서 경로를 사용자에게 확인한다. 경로를 말하지 않으면 `docs/code-audit.md` 를 제안한다.
- 범위를 **단위** 로 나눈다: 화면 단위 (ViewController·View 와 그 화면만 쓰는 타입) 와 공용 모듈 단위 (네트워크, 저장소, 공유 상태, 공용 UI 컴포넌트). 파일 하나는 단위 하나에만 속한다.
- 단위마다 코드를 한 번 훑어 읽고, 그 코드가 잘못될 수 있는 방식을 묶어 결함 **유형** 으로 정한다. 유형마다 무엇을 결함으로 볼지 한 줄씩 적는다.

## 2. 훑는다

단위 × 유형 표의 칸마다 그 단위의 코드를 그 유형으로 보고, 칸을 셋 중 하나로 채운다: 결함 있음 (결함 번호), 없음, 해당 없음.

훑다가 어느 유형에도 맞지 않는 결함을 찾으면 유형을 추가하고, 그 열의 다른 칸도 채운다.

표를 다 채우면 단위마다 유형 없이 한 번 더 읽는다: 유형을 기준으로 읽으면 그 밖의 결함은 보이지 않기 때문이다. 묻는 것은 하나다: 이 코드가 표의 유형 말고 다른 식으로 잘못될 수 있는가. 찾으면 유형을 추가하고 그 열을 채운다.

범위가 크면 단위 묶음이나 유형 묶음별로 서브에이전트에 맡긴다. 돌아온 결함은 SKILL.md 대로 재확인한다.

## 3. 결함마다 적는다

- **위치**: `file:line`
- **내용**: 무엇이 잘못됐는지 한두 문장
- **등급**: 근거 / 추론 / 모름
- **심각도**: 높음 (크래시, 데이터 손실, 핵심 기능 불가, 보안) / 중간 (잘못된 동작·표시, 성능 저하, 접근성 차단) / 낮음 (유지보수 위험)
- **사용자 영향**: 누가 언제 무엇을 겪는지
- **수정 위험**: 고치면 무엇이 흔들릴 수 있는지 (호출하는 곳의 수, 공유 상태, 테스트 유무)

등급이 모름인 결함은 심각도를 "확인되면 높음" 처럼 조건부로 적고, 결함 목록에서 근거·추론 결함 뒤에 둔다.

고칠지와 어떻게 고칠지는 보고서를 본 사용자와 정한다: 결함 항목에는 판단 재료까지만 적는다.

## 4. 실행 확인 목록

등급이 추론인 결함마다 증상 문장을 한 줄씩 적는다: 사용자가 겪을 일을 관찰할 수 있는 형태로 (예: "설정 화면을 닫아도 화면 객체가 해제되지 않는다"). 이 문장이 `ios-diagnosing-bugs` 를 호출할 때 Phase 1 의 입력이 된다.

## 보고서

```
# 코드 감사: <범위>

단위 N개, 유형 M개, 결함 K개 (높음 a, 중간 b, 낮음 c)

## 단위        ← 단위마다 속한 파일
## 유형        ← 유형마다 결함으로 보는 것
## 커버리지    ← 단위 × 유형 표
## 결함        ← 심각도 순, 3의 필드
## 실행 확인 목록
```

## 완료 기준

다음을 모두 만족할 때 끝난다:

- 범위의 모든 파일이 어느 단위에 속한다.
- 커버리지 표의 모든 칸이 채워졌고, 단위마다 유형 없이 다시 읽었다.
- 모든 결함에 3의 필드가 있고, 서브에이전트가 낸 결함은 직접 확인했다.
- 추론 결함마다 실행 확인 목록에 증상 문장이 있다.
- 보고서를 확인받은 경로에 썼다.
