# iOS Diagnosing Bugs

iOS 앱의 어려운 버그를 위한 규율이다. 단계는 이유를 밝힐 때만 건너뛴다.

증상으로 branch 를 하나 고르고, 해당 문서를 Phase 1 전에 읽는다:

- **크래시·잘못된 동작**: 이 문서만으로 진행한다.
- **느림·멈춤·끊김**: [PERF.md](PERF.md)
- **해제되지 않음·메모리 증가**: [MEMORY.md](MEMORY.md)

루프는 시뮬레이터에서 만든다. 다음 중 하나에 걸리면 [DEVICE.md](DEVICE.md) 를 읽고 실기기로 간다. 처음부터 걸리면 실기기에서 시작하고, 진행 중에 걸리면 어느 Phase 에서든 그 순간 전환한다:

- 증상이 실기기에서만 보고됐다 (특정 기종·OS 버전 포함).
- 시뮬레이터 루프를 조여도 red 가 되지 않는다.
- 증상이 시뮬레이터에 없는 하드웨어 (카메라, 센서, 햅틱, Bluetooth) 에 달려 있고, 캡처한 데이터 재생 (4번 루프) 으로 대신할 수 없다.
- 실기기 자원이 원인 후보다: 메모리 한도로 인한 종료, 발열, 성능 절대값.
- 시뮬레이터에서 고쳐 green 인데 실기기에서 여전히 재현된다.

코드베이스를 탐색할 때 용어집 (`GLOSSARY.md`, `CONTEXT.md` 등) 이 있으면 읽어 관련 모듈의 mental model 을 잡고, 손대는 영역의 ADR 을 확인한다. ADR 위치는 이 스킬 디렉토리 기준 `../grill-with-adr/ADR-FORMAT.md` 를 따른다.

## Redact

이 스킬은 명령, 출력, 캡처한 자료를 보여주게 한다. **모든 비밀값을 먼저 가린다**: 그 자리에 `<REDACTED>` 를 쓴다. 루프는 환경변수로 만들어 자격 증명이 보여주는 내용이 아니라 환경에 머물게 한다 (앱에는 `scripts/app-loop.sh --env NAME=VALUE` 로 넘긴다). 캡처한 자료에는 인증 헤더가 실려 있다: 신호를 담은 줄만 인용한다.

가린 출력으로 진단하기에 부족하면 그렇게 말하고 사용자에게 묻는다.

## Phase 1: 피드백 루프 만들기

**이것이 스킬이다.** 나머지는 기계적이다. 이 버그에 대해 **tight** 한 통과/실패 신호 (_이_ 버그에서 **red** 가 되는 것) 가 있으면 원인은 찾는다: bisect, 가설 검증, 계측은 모두 그 신호를 소비할 뿐이다. 신호가 없으면 코드를 아무리 들여다봐도 소용없다.

여기에 노력을 몰아준다. **공격적으로. 창의적으로. 포기하지 않는다.**

### 만드는 방법 (대략 이 순서로)

1. **실패하는 테스트**: 버그에 닿는 seam 의 XCTest 나 Swift Testing. 테스트 하나만 돌린다: `xcodebuild test -scheme <scheme> -destination 'platform=iOS Simulator,id=<UDID>' -only-testing:<타깃>/<타입>/<테스트>`. 테스트 타깃이 없으면 아래 루프로 먼저 red 를 만들고, 타깃은 Phase 5 에서 seam 을 정한 뒤 만든다.
2. **로그 단언 실행**: `scripts/app-loop.sh` 로 빌드·설치·실행하고, 증상을 드러내는 태그 로그 (Phase 4) 를 `--red-if`·`--red-unless` 로 단언한다. 문제 화면까지는 launch argument 나 환경변수 (`--env`) 를 읽어 앱이 바로 그 화면을 띄우게 하는 임시 진입 코드로 간다.
3. **UI 자동화**: XCUITest, 또는 `../ios-sim-test/SKILL.md` 의 시뮬레이터 조작 방법 (Maestro) 으로 화면을 조작하고 화면·로그로 단언한다. 시뮬레이터 설정이 조건이면 `xcrun simctl ui <UDID> content_size|appearance|increase_contrast <값>` 과 `../ios-sim-test/SIM-SETUP.md` 로 바꾼다.
4. **캡처한 응답 재생**: 실제 네트워크 응답·payload·이벤트를 파일로 저장해 `URLProtocol` stub 이나 테스트 fixture 로 그 코드 경로만 돌린다.
5. **임시 하네스**: 원본을 임시 디렉토리로 복사해 계측을 넣고 돌리거나, 문제 모듈 하나만 부르는 최소 테스트·앱을 만든다.
6. **반복·스트레스**: 가끔만 틀리면 `xcodebuild test ... -test-iterations <n> -run-tests-until-failure` 로 돌린다. 경쟁 상태가 의심되면 `-enableThreadSanitizer YES` 를 켠다.
7. **bisect 하네스**: 두 상태 (커밋, 데이터, OS 버전) 사이에 생긴 버그면 "그 상태로 빌드 → 확인" 을 자동화해 `git bisect run` 에 건다.
8. **차분 루프**: 같은 입력을 두 버전이나 두 설정 (Debug/Release, iOS 버전, 기기 크기) 에 돌려 출력을 비교한다.
9. **HITL 스크립트**: 최후 수단. 실기기 화면 조작처럼 사람이 해야 하면 이 스킬 디렉토리의 `scripts/hitl-loop.template.sh` 로 _그 사람을_ 구동해 루프를 구조화한다. 캡처한 출력이 다시 너에게 온다.

`scripts/` 의 각 파일은 머리 주석에 쓰는 법과 대신 처리하는 환경 함정을 적고 있다: 처음 쓸 때 읽는다. 그 밖의 블로킹 명령은 `scripts/with-timeout.sh` 로 끊는다 (macOS 에는 `timeout` 이 없다).

알맞은 루프를 만들면 버그는 90% 고쳐진 것이다.

### 루프 조이기

루프를 제품처럼 다룬다. 루프가 _하나_ 생기면 **tight** 하게 조인다:

- 더 빠르게 할 수 있나? (테스트 범위를 좁히고, 앱 루프는 문제 화면으로 바로 진입시키고, 관계없는 초기화를 건너뛴다. 코드가 그대로인 반복은 `--build` 없이 다시 실행만 한다.)
- 신호를 더 날카롭게 할 수 있나? ("죽지 않음" 이 아니라 구체적인 증상을 단언한다.)
- 더 결정적으로 할 수 있나? (시간과 랜덤 시드를 고정하고, 네트워크를 stub 으로 고정하고, 매 실행 앱을 새로 띄운다.)

30초 걸리고 들쭉날쭉한 루프는 없는 것보다 조금 나을 뿐이다. 2초짜리 결정적 루프는 tight 하고, 디버깅 초능력이다.

### 비결정적 버그

목표는 깔끔한 재현이 아니라 **더 높은 재현율** 이다. 트리거를 100번 반복하고, 병렬로 돌리고, 부하를 더하고, 타이밍 창을 좁히고, sleep 을 끼워 넣는다. 50% 로 재현되는 버그는 디버깅할 수 있고 1% 는 못 한다. 디버깅할 수 있을 때까지 재현율을 올린다.

### 루프를 정말 만들 수 없을 때

멈추고 그렇게 명시한다. 시도한 것을 나열한다. 사용자에게 요청한다: (a) 재현되는 환경에 대한 접근 (기기, OS 버전, 계정, 데이터), (b) 가린 캡처 자료 (크래시 로그 `.ips`, sysdiagnose, 타임스탬프가 있는 화면 녹화), (c) 테스트 빌드에 임시 계측을 넣을 권한. 루프 없이 가설로 넘어가지 **않는다**.

### 완료 기준: red 가 되는 tight 한 루프

루프가 **tight** 하고 **red 가 될 수 있을 때** Phase 1 이 끝난다. **명령 하나** (스크립트 경로, 테스트 호출, launch + grep) 의 이름을 댈 수 있고, 그 명령을 **이미 한 번 이상 실행했고** (호출과 출력을 가려서 보여준다), 다음을 모두 만족한다:

- **red 가 될 수 있다**: 실제 버그 코드 경로를 돌리고 **사용자가 말한 바로 그 증상** 을 단언하므로, 이 버그에서 red 가 되고 고치면 green 이 된다. "에러 없이 돈다" 가 아니다. _이 버그_ 를 잡을 수 있어야 한다.
- **결정적이다**: 매번 같은 판정이다 (비결정적 버그는 위처럼 고정된 높은 재현율).
- **빠르다**: 분이 아니라 초 단위다. 빌드 포함 수십 초가 걸리면 위 루프 조이기대로 줄인다.
- **에이전트가 돌릴 수 있다**: 사람 없이 돌릴 수 있다. 사람이 끼면 `scripts/hitl-loop.template.sh` 로만.

이 명령이 있기 전에 이론을 세우려고 코드를 읽고 있다면 **멈춘다: 곧장 가설로 뛰어드는 것이 이 스킬이 막는 바로 그 실패다.** red 가 되는 명령이 없으면 Phase 2 도 없다.

## Phase 2: 재현 + 최소화

루프를 돌린다. 버그가 나타나며 red 가 되는 것을 본다.

다음을 모두 확인한 뒤 넘어간다:

- 루프가 **사용자가** 말한 실패를 만든다. 근처에서 우연히 나는 다른 실패가 아니다. 엉뚱한 버그 = 엉뚱한 수정.
- 여러 번 돌려도 재현된다 (비결정적 버그는 디버깅할 만큼 높은 재현율로).
- 나중 단계가 수정을 검증할 수 있도록 정확한 증상 (에러 메시지, 잘못된 출력, 느린 시간) 을 캡처했다.

### 최소화

red 가 되면 재현을 **여전히 red 인 가장 작은 시나리오** 로 줄인다. 입력, 호출자, 설정, 데이터, 단계를 **하나씩** 잘라내고 자를 때마다 루프를 다시 돌려, 실패를 떠받치는 것만 남긴다.

이유: 최소 재현은 Phase 3 의 가설 공간을 줄이고 (의심할 부품이 줄어든다), Phase 5 의 깨끗한 회귀 테스트가 된다.

**남은 요소가 모두 떠받치는 것** 일 때 끝난다: 하나라도 빼면 루프가 green 이 된다.

재현 **그리고** 최소화를 마치기 전에는 넘어가지 않는다.

## Phase 3: 가설

검증을 시작하기 전에 **순위를 매긴 가설 3~5개** 를 만든다. 가설을 하나만 만들면 처음 떠오른 그럴듯한 생각에 닻을 내린다.

각 가설은 **반증할 수 있어야** 한다: 그 가설이 하는 예측을 적는다.

> 형식: "<X> 가 원인이면, <Y 를 바꾸면> 버그가 사라지고 / <Z 를 바꾸면> 더 나빠진다."

예측을 적을 수 없으면 그 가설은 느낌이다: 버리거나 날카롭게 한다.

**검증 전에 순위 목록을 사용자에게 보여준다.** 사용자는 순위를 바로 바꿀 도메인 지식 ("방금 #3 쪽을 배포했어요") 이나 이미 배제한 가설을 알고 있는 경우가 많다. 싸고 시간을 크게 아끼는 확인 지점이다. 막히지는 않는다: 사용자가 자리에 없으면 내 순위대로 진행한다.

## Phase 4: 계측

각 probe 는 Phase 3 의 특정 예측 하나에 대응한다. **한 번에 변수 하나만 바꾼다.**

도구 순서:

1. **디버거 (LLDB)** 를 쓸 수 있으면 breakpoint 하나가 로그 열 줄보다 낫다.
2. 가설을 가르는 경계에 **태그 로그** 를 둔다. 찍는 지점은 그 경계뿐이다.

**모든 디버그 로그에 고유 접두어를 붙인다**: `print("[DEBUG-a4f2] ...")`. 끝날 때 정리가 grep 한 번이 된다. 태그 없는 로그는 살아남고, 태그 있는 로그는 지워진다.

**성능 branch**: 로그는 대개 틀린 도구다. [PERF.md](PERF.md) 대로 기준 측정을 세운 뒤 bisect 한다. 측정 먼저, 수정은 나중.

**메모리 branch**: [MEMORY.md](MEMORY.md) 의 도구로 누가 객체를 잡고 있는지 확인한다.

## Phase 5: 수정 + 회귀 테스트

회귀 테스트는 수정 **전에** 쓴다. 단 **올바른 seam** 이 있을 때만. Skill 도구로 "tdd" 스킬을 호출해 그 규칙대로 쓴다: 테스트할 seam 을 사용자와 합의하고, red 를 먼저 본다. 사용자가 자리에 없으면 추천 seam 과 이유를 기록하고 진행한다.

올바른 seam 은 호출처에서 일어나는 **실제 버그 패턴** 을 테스트가 그대로 돌리는 곳이다. 쓸 수 있는 seam 이 너무 얕으면 (버그에는 여러 호출자가 필요한데 호출자 하나짜리 테스트, 버그를 일으킨 연쇄를 재현하지 못하는 단위 테스트) 거기에 쓴 회귀 테스트는 거짓 확신을 준다.

**올바른 seam 이 없으면 그것 자체가 발견이다.** 기록한다. Skill 도구로 "codebase-design" 스킬을 호출해 그 용어 (seam, interface, depth) 로, 코드베이스 구조가 버그를 가두지 못하게 막고 있다고 보고한다.

올바른 seam 이 있으면:

1. 최소 재현을 그 seam 의 실패하는 테스트로 바꾼다.
2. 실패하는 것을 본다. 코드나 fixture 를 바꿔 red 를 억지로 만들었다면, 원본 복사본과 `diff` 해 그 변경이 실제로 들어갔는지 증명한 뒤 믿는다.
3. 수정한다.
4. 통과하는 것을 본다.
5. Phase 1 피드백 루프를 원래 (최소화 전) 시나리오로 다시 돌린다.

## Phase 6: 정리

다음을 모두 확인해야 끝난다. 끝났다고 보고할 때 항목마다 확인한 근거 (명령과 출력) 를 함께 적는다:

- 원래 재현이 더 이상 재현되지 않는다 (Phase 1 루프 재실행)
- 회귀 테스트가 통과한다 (또는 seam 이 없음을 기록했다)
- `[DEBUG-...]` 계측을 모두 지웠다 (접두어로 grep)
- 임시 진입 코드, 임시 하네스, 앱에 복사한 probe 파일을 지웠다 (또는 분명히 표시한 디버그 위치로 옮겼다)
- 바꾼 시뮬레이터 설정을 원래대로 돌렸다 (실기기를 썼으면 [DEVICE.md](DEVICE.md) 의 정리도 마쳤다)
- 맞은 가설을 커밋·PR 메시지에 적어 다음 사람이 배우게 했다
